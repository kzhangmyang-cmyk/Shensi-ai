# 抖音公开线索主体自动核验设计

**日期：** 2026-08-08

**状态：** 已确认设计，待实施计划

**范围：** 抖音公开视频、评论信号与短链接形成的未解析个人候选

## 1. 目标

将目前会停在“主体未解析”的抖音公开线索自动推进到 AI 研判闭环：

```text
公开视频 / 评论信号 / 短链接
→ 受控解析公开页面
→ 提取候选抖音主页
→ 独立搜索证据交叉验证
→ 确定性身份门禁
→ 自动确认主体
→ 客户研究
→ 意向评分
→ 财务价值评分
→ 客户作战卡
```

系统只在证据形成唯一且可复核的共识时自动确认。证据不足、互相冲突或访问受限时，不猜测、不修改候选身份，转入现有人工核验工作台。

## 2. 非目标与边界

- 不新增抖音评论、私信、加好友或群发能力。
- 不使用浏览器模拟、客户端控制、逆向协议或绕过平台限制的方式解析身份。
- 不扩展快手、小红书、微博、微信公众号等新平台。
- 不让大模型直接决定或提交主体身份。
- 不新建第二套评分、作战卡或人工审核系统。
- 不自动写入 CRM；主体确认后的流程继续沿用现有审核与交接规则。

## 3. 核心设计原则

### 3.1 智能体负责调度，工作流负责核验

该能力实现为一个确定性的 `DouyinIdentityResolutionStage`，由获客智能体在候选进入研究前调度。工作流使用现有公开抓取、搜索连接、证据存储、身份确认和智能研判能力，不引入一个可以自由猜测身份的新智能体。

大模型可以在后续客户研究中总结公开资料，但主体核验门禁只依赖规范化 URL、证据来源、访问状态、唯一性、候选版本和冲突检查。

### 3.2 失败关闭

任一条件不满足时，系统保持 `identityResolved=false`。失败结果必须包含机器可读原因和可供人工复核的证据，不以概率阈值代替事实门禁。

### 3.3 复用现有闭环

自动核验成功后，调用现有身份确认服务，再调用现有 `createAfterIdentity` 智能研判入口。研究、意向评分、财务价值和作战卡不另写并行实现。

## 4. 组件与数据流

### 4.1 输入

工作流只接受：

- 平台为 `douyin`；
- 类型为个人候选；
- `identityResolved=false`；
- 已保存至少一条公开来源证据；
- 原始来源为抖音 HTTPS 视频、评论信号、短链接或主页链接。

输入快照至少包含 `candidateId`、`candidateVersion`、原始证据 ID、来源 URL 和来源指纹。

### 4.2 受控公开解析

工作流读取已有公开证据，并在需要时执行受控抓取：

1. 只允许 HTTPS。
2. 只允许配置中的抖音公开域名及其明确批准的短链接域名。
3. 记录完整重定向链；任何一步离开白名单即停止。
4. 从公开页面的明确作者链接、规范链接或结构化公开字段中提取 `/user/<sec_uid>`。
5. 页面访问受限、需要登录、验证码、已删除或无法验证时，不尝试绕过。

解析产生第一类证据：

- `douyin_public_page`：抖音公开页面或其合法重定向链明确指向规范化用户主页。

### 4.3 独立搜索交叉验证

工作流使用已启用的真实搜索连接，根据原始内容标识、视频 URL、可见标题和作者线索执行限定域名搜索，并保存搜索请求与结果证据。

搜索结果只有在其目标 URL 可规范化为同一个 `/user/<sec_uid>` 时才计入共识。搜索摘要中只出现昵称、但没有可验证主页 URL，不足以确认身份。

该步骤产生第二类证据：

- `independent_search_result`：独立搜索提供商返回并可验证的规范化抖音用户主页。

同一次页面抓取中的多个字段、同一搜索结果的多个摘录或同一来源的重复 URL，只算一份证据。独立性按证据来源类别和来源指纹判断。

### 4.4 规范化与去重

所有候选主页必须统一为规范化 HTTPS 抖音 `/user/<sec_uid>` URL。工作流按规范 URL 去重，并保留每个 URL 对应的证据集合、访问状态和来源类别。

不接受 `/video/`、短链接、搜索结果页或其他非 `/user/` URL 作为最终主体。

## 5. 自动确认门禁

仅当以下条件全部满足时，结果为 `verified_consensus`：

1. 去重后恰好剩下一个规范化 `/user/<sec_uid>`。
2. 该主页至少拥有一份 `douyin_public_page` 证据。
3. 同一主页至少拥有一份 `independent_search_result` 证据。
4. 两类证据具有不同来源指纹，不是同一页面或同一结果的复制。
5. 相关页面可公开访问，且未标记为受限、失效或不可信。
6. 不存在指向其他主页的有效冲突证据。
7. 提交前候选版本仍等于工作流输入的 `candidateVersion`。

系统不使用“80% 置信度”一类模型概率自动放行。门禁输出是确定性的 `verified_consensus` 或具体失败原因。

## 6. 成功路径

门禁通过后：

1. 将两类证据的 ID、规范主页 URL、候选版本和可读核验理由提交给现有 `AcquisitionIdentityResolutionService`。
2. 服务端再次验证证据归属、访问状态、平台、URL 类型和候选版本。
3. 身份确认成功后，候选变为 `identityResolved=true`。
4. 以幂等方式调用现有 `createAfterIdentity`。
5. 自动继续现有客户研究、意向评分、财务价值评分与客户作战卡流程。
6. 刷新或进程恢复后，从服务端状态继续，不依赖浏览器内存中的临时状态。

## 7. 失败与人工回退

下列结果不得修改候选身份，并进入现有人工核验工作台：

| 结果码 | 含义 | 人工界面建议 |
| --- | --- | --- |
| `not_found` | 未找到规范用户主页 | 展示原始公开证据，允许填写精确 `/user/` |
| `insufficient_evidence` | 只有一种独立证据类别 | 标明缺少抖音页证据或独立搜索证据 |
| `ambiguous` | 存在多个有效候选主页 | 并列展示候选及各自证据 |
| `conflicting` | 两类证据指向不同主页 | 突出冲突来源，不预填最终主页 |
| `access_restricted` | 页面需要登录、验证码或无法公开验证 | 保留访问状态，不尝试绕过 |
| `redirect_not_allowed` | 重定向离开允许域名 | 展示被阻断的重定向链 |
| `stale_candidate` | 候选版本在处理期间变化 | 重新读取最新候选后再运行 |
| `provider_unavailable` | 搜索或抓取服务暂不可用 | 提供安全重试，不把系统故障当身份否定 |

人工确认仍须使用精确 HTTPS 抖音 `/user/` URL、版本化请求、证据 ID、理由和幂等键。确认后复用相同的自动续跑研判入口。

## 8. 状态与界面

复用当前主体核验工作台，不新增弹窗或第二套详情页。增加以下可观察状态：

- `正在自动核验`：显示当前步骤，不展示模型内部推理。
- `已自动确认，正在进行 AI 研判`：展示规范主页和两类证据。
- `证据不足，需要人工确认`：展示失败原因、候选主页和原始证据。
- `自动核验暂时失败，可重试`：仅用于可恢复的提供商或网络故障。

页面不得把视频 URL 或短链接预填到用户主页输入框。所有结论展示证据来源、核验时间和状态。

## 9. 幂等、并发与恢复

- 自动核验操作键由 `candidateId + candidateVersion + sourceEvidenceFingerprint` 构成。
- 同一操作重放返回原结果，不重复写身份确认记录。
- 身份确认请求继续使用服务端现有幂等键和候选版本检查。
- 智能研判创建继续使用现有幂等机制，确保只创建一次有效操作。
- 并发任务中先成功确认的一方使后续旧版本提交失败为 `stale_candidate`。
- 可恢复故障保留当前操作和证据；重试从服务端持久状态继续。

## 10. 可观测性

每次自动核验记录：

- 候选、版本和来源证据指纹；
- 受控抓取与搜索提供商请求结果；
- 规范化前后的候选主页；
- 每份证据的类别、来源指纹和访问状态；
- 门禁结果及失败原因；
- 身份确认操作 ID；
- 后续智能研判操作 ID。

日志和 API 响应不得包含客户配置的完整 API Key。

## 11. 验收标准

### 11.1 自动成功

- 视频或评论信号形成未解析候选。
- 抖音公开页证据与独立搜索证据共同指向唯一 `/user/`。
- 身份只确认一次，并自动启动一次智能研判。
- 最终可读取意向评分、财务价值和客户作战卡。

### 11.2 安全回退

- 两个不同主页同时有效时，不自动确认。
- 只有单一证据类别时，不自动确认。
- 页面受限或重定向离开白名单时，不自动确认。
- 候选版本变化时，不提交旧结果。
- 失败后人工核验仍可完成确认并继续研判。

### 11.3 恢复与无重复

- 搜索提供商短暂失败后可安全重试。
- 重放同一操作不会创建重复身份记录或重复智能研判。
- 浏览器刷新或服务重启后可恢复状态。

### 11.4 端到端

- 真实模式下完成“抖音公开视频线索 → 自动主体核验 → 客户研究 → 意向评分 → 财务价值 → 作战卡”。
- 全链路没有自动评论、私信、加好友、群发或自动 CRM 写入。

## 12. 实施约束

- 先写会失败的测试，再写最小实现。
- 优先扩展现有身份确认、证据、操作与研判服务，不创建平行领域模型。
- 前端只展示服务端权威状态，不自行判断身份共识。
- 每个提交保持单一目的，并保留当前工作区中用户未提交的 `pnpm-workspace.yaml`。
