# AI 全自动获客与销售转化系统——抖音首发版 PRD

日期：2026-08-05

状态：阶段 A 公开搜索、用户公开链接与一级评论样本 Beta 已实现；授权连接器与
自动动作仍在后续阶段

适用基线：GoodJob 1.09 + GoodJob Marketing System Frontend

项目负责人：用户本人

开发方式：用户统一决策与验收，Codex 按 GitHub Issue 分支实现、测试和提交

## Problem Statement

中国市场上的许多“AI 获客”产品，本质仍是关键词脚本、批量采集和机械触达。它们能够增加动作数量，却难以回答以下真正影响成交的问题：

1. 哪些公开互动和需求信号构成真实商机；
2. 同一个用户在多个内容和时间窗口中的行为是否应合并判断；
3. 哪个客户既有意向，又有足够的财务价值；
4. 应该找哪个角色、从什么需求切入、使用哪种沟通策略；
5. 哪些动作可以在客户预授权和平台实际能力范围内自动完成；
6. 哪些异常、敏感、低置信度或高风险场景必须由人工接管；
7. 从发现、互动、进入私域、成交到回款，是否能够完整归因并持续优化。

GoodJob 1.09 的通用公开搜索、证据留存、主体归一、资格评分、财务价值、客户
作战卡、审核、CRM 转换和结果反馈已经接入新的营销前端。当前抖音阶段在该内核上
增加了可审批的公开搜索、客户公开链接入口、有界一级评论样本、不可变评论事件、
采集观测、需求信号聚合和真实 Run Presentation。正式页面读取服务端持久化事实，
不再用前端倒计时、随机数量或假评论模拟运行。

当前发布定位为“审批后自动发现和研判、动作前人工决策”的只读 Beta。它帮助客户
从公开可见的有限样本中识别值得继续研究的需求信号，但不声称扫描整个抖音，不读取
私域内容，也不自动评论、私信、加好友、群发或转换 CRM。客户授权的抖音官方
OAuth 连接器、持久化周期调度和官方动作执行继续沿用相同领域边界，在后续阶段实现。

## Solution

产品采用“一个 AI 增长参谋 + 多个纯函数 Skill + 确定性工作流 + 受控来源适配器
+ 人工门禁”的架构，而不是堆叠多个相互自由对话的 Agent。官方平台连接器和动作
规则引擎是同一架构的后续扩展点，不是本期已交付能力。

### 1. 用户可见产品形态

用户只面对一个“AI 增长参谋”。它负责：

- 理解行业、地区、产品、目标客户和经营目标；
- 生成可解释的抖音获客计划；
- 汇报任务进度、优先客户、推荐原因和下一步动作；
- 接受老板、销售、运营和财务角色的自然语言追问；
- 将用户确认转化为计划、规则、预算或任务，而不是仅返回聊天文字。

后台专业能力以 Skill 和工作流存在，包括 ICP、搜索规划、公开评论标准化、身份
合并、意向评分、财务价值、客户研究、作战卡和连接策略草稿。报价保护、对话跟进、
官方动作策略和结果学习属于后续阶段。

### 2. 抖音首发获客闭环

```text
自然语言经营目标
→ AI 生成抖音获客计划
→ 用户确认公开来源、一级评论样本上限、预算和模型快照
→ 官方搜索 API 发现公开视频 / 用户提交公开抖音链接
→ experimental_public_sample 读取有界一级公开评论样本
→ 不可变评论事件、采集观测、证据、去重与主体信号聚合
→ 主体身份研究与资格评分
→ 财务价值、客户研究与客户作战卡
→ 人工审核
→ 仅在当前门禁通过后人工确认 CRM 转换或后续触达任务
```

### 3. 当前数据入口

1. **公开搜索发现**：通过客户配置的官方搜索 API，检索公开可访问的抖音页面、账号、视频、话题和相关网页。
2. **用户提供内容**：用户提交公开抖音链接、Excel/CSV 或经过授权导出的业务数据。
3. **公开一级评论样本**：只对前两类入口中解析出的受支持公开视频运行
   `experimental_public_sample`；覆盖语义固定为 `public_top_level_sample`。

客户授权的抖音官方连接器仍是后续入口，当前不得显示为已连接。界面必须清晰展示
每条数据的来源方式、更新时间、覆盖和访问状态，不能把公开搜索或一级样本描述为
“扫描整个抖音”，也不能把未获授权的能力展示为可用。

### 4. AI 的真实价值

AI 不只生成文案，而是承担以下语义决策：

- 将用户自然语言经营目标转为结构化 ICP 与获客计划；
- 从评论、账号主页、内容主题、重复互动、明确询价、业务痛点和负向信号中提取商机信号；
- 将单点行为放入时间窗口和主体上下文中综合判断；
- 输出 S/A/B/C/D 意向等级、财务价值、证据、置信度和反证；
- 推测现有供应商、决策链、采购偏好和商务沟通风格，并严格区分事实、推测和未知；
- 生成不同渠道的连接策略草稿，但不直接发送；
- 结合人工记录的成交、回款、拒绝和流失结果评估信号与策略版本。

### 5. 自动化边界

本期“自动化”只指：一个 Run 获得人工审批后，服务端按固定顺序执行公开搜索、
视频 ID 解析、一级评论样本读取、不可变事件归一、公开主体信号聚合和资格研判，
并持续发布真实时间线。自动化不延伸到外联或 CRM 转换。

页面默认上限是每 Run `10` 个视频、每视频 `30` 条评论、每视频 `3` 页；合同硬
上限是 `20 / 100 / 5`。评论 HTTP 请求和接收结果继续占用 Run 的请求、结果、费用
和时长预算。终态计划可以由客户点击“再次运行”创建独立 Run，但当前没有持久化
日/周/Cron 调度器；启动和周期 recovery sweeper 只恢复已经存在的 execution。

Provider 只访问代码白名单内的 HTTPS 抖音公开主机，不接受自定义 endpoint，不
使用 Cookie、登录态、私有签名、代理、验证码或浏览器模拟。当前只读一级评论
正文；二级回复只记录公开数量，不读取正文，也不保存评论者头像。任何缺失能力都
必须保持受限、人工审核或失败状态，不能通过逆向协议或“模拟真人频率”补齐。

### 5.1 身份、错误与重跑语义

评论先形成不可变平台事件和追加式采集观测，再生成 Evidence 和候选；同一租户的
同一平台评论 ID 幂等，新的采集或原文版本不覆盖历史事件。严格 `sec_uid` 只作为
稳定但尚未核验的主体键，用于同一公开主体聚合；仅有 `sec_uid`、handle 或缺少稳定
主体时都保持 `needs_research`。受控公开搜索和精确公开主页证据能够形成一致身份时
可继续资格链路，否则必须停在人工核验。单条
“多少钱”最多属于潜在信号；未核验强信号显示“高潜需求信号”，不能显示为已确认
高意向客户。

- `partial_success`：同 Run 有成果也有失败，保留全部成功事件；
- `no_public_comments`：本次一级公开样本为空，不表示没有客户；
- `access_restricted` / `rate_limited`：访问或频率受限，保留已有结果；
- `public_sample_unavailable`：Beta 公开样本暂不可用；
- `video_id_unresolved`：未解析出受支持的公开数字视频 ID；
- `source_payload_invalid`：公开响应缺少平台 ID 或不符合严格合同。

成功、空成功、部分成功或失败 Run 结束后，客户可在已批准计划上点击“再次运行”
创建独立 Run。历史事件、observation、Evidence 和旧 Run 投影保持可追溯；精确
execution 重放复用已持久的终态结果，不重复请求 Provider。

普通测试和 CI 只用 fixture。真实网络只允许显式手工执行：

```bash
DOUYIN_VIDEO_ID='<公开视频数字 ID>' \
DOUYIN_PUBLIC_COMMENT_SMOKE=1 \
npm run smoke:douyin-public-comments --workspace backend
```

缺少开关或 ID 时不得发请求；endpoint 不可用时保持 Beta 熔断/受限状态，不改用
Cookie、签名、代理或规避实现。

### 6. 跨行业能力

系统不绑定单一垂直行业。行业差异通过租户级配置和知识库表达：

- 产品与服务资料；
- ICP、排除画像和需求信号；
- 成交案例、常见异议和禁用承诺；
- 价格、成本、毛利、回款和折扣规则；
- 角色、采购链和渠道策略；
- 行业词库与评估样本。

平台连接器、证据、工作流、审核、CRM 和财务模型保持通用。

## User Stories

### 获客计划与配置

1. 作为老板，我希望用一句话描述产品、行业、地区和目标客户，让 AI 生成可执行的抖音获客计划。
2. 作为运营，我希望查看并修改 AI 生成的关键词、需求信号、排除条件、数据来源和预算。
3. 作为管理员，我希望为抖音计划启用一级公开评论样本，并设置每 Run 视频、每视频评论和页数上限。
4. 作为管理员，我希望计划明确显示 `experimental_public_sample` 的 Beta、只读和非完整覆盖边界。
5. 作为老板，我希望确认当前 Run 只做公开发现和研判，所有外联与 CRM 转换仍由人工门禁控制。
6. 作为财务负责人，我希望为计划设置请求量、结果量、模型费用、搜索费用和总时长上限。
7. 作为团队成员，我希望计划审批后固化模型、提示词、规则、连接器和预算快照，避免执行时静默变化。

### 商机发现与证据

8. 作为运营，我希望系统通过公开搜索发现与目标行业、地区和需求相关的抖音页面及账号。
9. 作为运营，我希望手动提交抖音公开链接，并让系统沿用同一套清洗、去重和评分流程。
10. 作为管理员，我希望单个视频访问失败时保留同 Run 已获得的事件，并看到稳定错误码和 `partial_success`。
11. 作为销售，我希望每条候选都展示原始来源、时间、证据摘要和访问状态。
12. 作为销售，我希望同一账号在多个视频、评论和时间点的行为合并成一个候选，而不是重复客户。
13. 作为销售，我希望一句“多少钱”不会自动成为高意向，系统必须结合账号匹配、重复互动、业务场景和负向信号。
14. 作为审核员，我希望身份不明确的候选停留在待研究状态，而不是被 AI 猜成真实客户。

### AI 评分、研究与作战卡

15. 作为销售，我希望系统给每条候选输出 S/A/B/C/D 等级、分数、证据、反证、置信度和推荐动作。
16. 作为老板，我希望系统同时判断客户是否想买和是否值得做，优先展示高意向、高毛利、快回款客户。
17. 作为销售，我希望系统研究客户企业、近期动态、需求、疑似供应商和替代或补位机会。
18. 作为销售，我希望系统识别可能的需求发起人、影响者、采购、技术和最终决策人。
19. 作为销售，我希望系统根据公开商务证据和历史沟通推测采购偏好与沟通风格，并明确标注置信度。
20. 作为销售，我希望系统为高优先级客户自动生成客户作战卡，无需逐条点击。
21. 作为销售，我希望针对老板、运营、采购、技术和一线使用者得到不同开场策略。
22. 作为销售，我希望作战卡同时列出不建议动作，防止直接报价、过度承诺或无依据断言。

### 后续：官方自动动作与人工接管

31. 作为管理员，我希望能够随时暂停计划、撤销自动动作授权并停止待执行任务。

## Implementation Decisions

### 1. 复用现有 GoodJob 领域内核

继续使用现有 Plan、Run、Shard、Candidate、Evidence、Qualification、Financial Value、Battle Card、Review、CRM Conversion 和 Outcome Feedback。不得为抖音另建一套平行的候选、评分或 CRM 数据模型。

### 2. 来源适配器与后续平台连接器边界

搜索 Provider 与内容来源平台必须分离：

- `SearchProvider` 表示百度、腾讯、Tavily 等“如何发现网页”；
- `PublicSampleProvider` 表示当前如何有界读取公开视频的一级公开评论样本；
- `PlatformConnector` 表示后续如何授权读取平台数据或执行官方动作；
- `sourcePlatform` 表示证据内容实际来自哪个平台。

当前只信任固定快照：connection ID 为 `douyin-public-comments`，Provider ID 为
`experimental_public_sample`，类型为 `content_fetch`，状态为 `active`，凭据版本
为 `1`；不让客户选择或修改 endpoint。后续官方连接器才保存
租户、账号、授权范围、能力快照、凭据版本、Webhook/Poll 模式、同步游标、状态、
到期时间和限额。

### 3. 新增平台事件证据与信号聚合

公开评论先标准化为不可变事件和追加式 observation，再聚合为候选信号。事件包含
平台、视频、一级评论平台 ID、主体公开标识、原文哈希、发生与捕获时间、Provider
版本、覆盖、制品哈希和访问状态。缺少平台评论 ID 时记录
`source_payload_invalid`，不创建事件；重新采集不覆盖事件原文。

资格评分读取聚合信号，不直接把单条评论当作客户结论。新事件到达后，按候选和决策版本幂等触发重评。

### 4. Agent、Skill、工作流和规则严格分层

- **AI 增长参谋 / Pi**：理解目标、选择已注册 Skill、解释结果，不直接持有平台凭据或执行外部动作。
- **Skill**：接受版本化输入，返回结构化建议和证据引用；无数据库写入、无网络副作用、无消息发送。
- **确定性工作流**：负责任务顺序、队列、预算、限流、重试、暂停、恢复、幂等和状态机。
- **硬门禁**：身份、证据、勿扰、明确拒绝、预算和 Schema 规则优先于模型建议。
- **后续规则引擎 / 平台连接器 Worker**：对官方动作输出自动、审核或禁止结论，
  并保存真实回执；当前尚未安装。

### 5. 后续自动动作领域模型

后续新增 `ActionPolicy`、`PlatformActionIntent`、`ActionDecision`、`ActionJob` 和
`ActionReceipt`。它们不是当前公开评论 Beta 的已发布接口。动作意图不能直接执行；
规则引擎必须基于能力、授权、计划快照、勿扰、频率、预算、内容和幂等状态生成决定。

第一阶段的动作类型由抖音连接器实时能力探测决定。代码不得假定所有账号均支持评论回复、主动私信、群消息或其他动作。

### 6. 前端采用聚合投影，不复制领域写逻辑

将新营销前端的“获客任务”映射为 `AcquisitionPlan + latest AcquisitionRun`，增加只读首页和任务聚合投影；所有创建、审批、运行、审核和转换继续调用 GoodJob 的权威接口。

前端保留现有视觉语言，但逐步拆出结构化组件和 API 状态层，不继续扩展硬编码 DOM 演示数据。

### 7. 契约真源先收口

在平台开发前，统一实际运行时 OpenAPI 与仓库中的契约 YAML，明确唯一真源。所有新接口必须同时提供 JSON Schema、OpenAPI、错误码、幂等和并发语义。

### 8. BYOK 与租户隔离

客户继续填写自己的官方模型和搜索 API 凭据。凭据服务端加密、只返回掩码，运行
绑定凭据版本和能力快照。当前公开评论 Provider 不要求或接收抖音账号凭据；平台
应用凭据只会在后续官方连接器中引入。团队、租户和账号数据严格隔离。

### 9. 开源项目使用原则

相关开源仓库只放入独立参考源码区，并写入来源、commit、许可证和用途清单。允许的复用方式取决于许可证；GPL 或无许可证仓库只做架构研究，禁止把代码复制到闭源生产仓库。所有引入生产依赖均需单独决策记录和安全审计。

## Testing Decisions

### 1. 契约接缝

- JSON Schema 校验所有 Skill 输入输出、平台事件、动作策略和回执；
- OpenAPI 覆盖真实运行路径、错误码、ETag、`If-Match` 和 `Idempotency-Key`；
- 增加契约漂移检查，禁止运行时代码和静态 YAML 再次分叉。

### 2. 领域闭环接缝

覆盖：

```text
Plan → Run → Search / Public Comment Event → Evidence → Signal Aggregate
→ Candidate → Identity Gate → Qualification → Financial Value → Battle Card
→ Human Review → CRM → Outcome
```

验证不可变事件、追加式观测、主体聚合、身份门禁、重新评分、部分失败、暂停恢复、
再次运行、预算耗尽、明确拒绝和勿扰门禁。

### 3. 平台适配器接缝

使用本地 Fixture 和注入的 HTTP transport 覆盖：

- 直接视频 URL、公开分享 URL、受控短链解析和不受支持 URL；
- 同页/跨页重复、游标不前进、429、`Retry-After`、5xx、超时和中止；
- 受限响应、空公开样本、缺少平台评论 ID 和字段规范化；
- 租户隔离、事件幂等、追加式 observation、内容版本和 Run 投影重放；
- `sec_uid`、handle、不可合并主体，以及正向、负向和噪音黄金样本；
- 不包含头像、Cookie、登录、签名、代理、浏览器模拟或写动作字段。

自动测试默认不访问真实抖音网络。

### 4. Skill 黄金样本

建立跨行业中文样本集，至少覆盖：

- 单句弱信号；
- 多次互动叠加强信号；
- 明确询价但行业不匹配；
- 同行、广告、拒绝和投诉；
- 高意向低财务价值；
- 低意向高潜在价值；
- 无证据的供应商和性格推测；
- 报价、异议和跟进阶段变化。

每个版本记录精确率、召回率、越权动作率、无证据断言率、人工改判率和成本。

### 5. 前端状态机接缝

覆盖 idle、planning、awaiting approval、running、partial success、paused、connection required、capability unavailable、review required、completed 和 failed。真实模式不允许回退为假进度或演示数字。

### 6. 端到端发布接缝

公开评论自动化 E2E 显式提交不可变 queued、running、`partial_success` 服务端
快照，再由真实轮询读取。它覆盖 1440、1024、768 视口、刷新恢复、长评论折行、
评论到候选/Evidence 回溯和无横向溢出；除 GET/HEAD/OPTIONS 外不能产生写请求，
也不能访问抖音外网。任何未声明的获客请求返回 `501` 并使测试失败。

授权可见评论读取 E2E 进一步用严格页面消息 harness 穿透真实 UI/controller/API，
覆盖 1440、1024、768、键盘授权、扩展缺失、DOM 优先、遮挡 WebP OCR fallback、
低置信人工复核、停止、安全拒绝、服务端刷新恢复、授权/到期制品和无横向溢出。
fixture 必须审计请求、日志、浏览器存储及自身持久状态；禁止真实扩展、真实抖音网络、
原始视口、Cookie、浏览器配置、互动写动作和自动 CRM 转换。候选 Evidence 仅在
`authorized_visual_observation.artifactId` 非空时提供遮挡裁剪入口；制品到期仍显示
Evidence ID 与 hash。运行命令为：

```bash
cd /path/to/GoodJob-marketing-system-frontend
npm run test:e2e -- acquisition-visual-reader.spec.ts
```

真实 Chrome 只允许显式 `GOODJOB_VISUAL_READER_SMOKE=1` 的人工 Beta smoke；操作者
必须亲自选择自己的公开视频并点击开始。输出仅可包含会话状态、有界数量、提取方法和
稳定错误码，不能包含评论正文或个人字段，且不得进入 CI。Chrome 扩展程序页移除扩展
即完成卸载；服务端 Evidence 不随扩展卸载而删除，遮挡制品按保留期到期。

## Out of Scope

首个抖音发布里不包含：

- 快手、小红书、微博、微信公众号的真实连接器；
- 客户授权的抖音官方 OAuth 连接器、Webhook、授权事件同步和官方动作执行；
- 持久化日/周/Cron 获客调度；当前 recovery sweeper 只恢复已创建的 execution；
- 非官方协议、客户端 Hook、逆向接口、验证码绕过或设备农场；
- 模拟真人频率以规避平台检测；
- 采集非公开聊天、通讯录、私人朋友圈、家庭住址、轨迹、健康、宗教、金融账户等敏感或私密信息；
- 在没有平台能力和用户授权时主动联系陌生人；
- 用模型推测代替身份、供应商、采购需求或动作回执事实；
- 保证不封号、保证成交、保证 ROI 或保证回款；
- 第一阶段重做完整 CRM、ERP、财务会计系统或企业级 EPM；
- 3D 数字人、语音克隆或只增加视觉噱头的“贾维斯”动画。

## Further Notes

### 发布阶段

1. **阶段 A：真实展示闭环**

   当前已落地：统一契约与新前端，完成公开搜索、用户公开链接、有界一级评论
   样本、不可变事件、需求信号、身份/资格门禁、真实时间线和人工审核入口。

2. **阶段 B：授权数据闭环**

   接入抖音官方 OAuth、能力探测、授权数据/事件同步、游标和 Webhook。

3. **阶段 C：受控自动转化**

   上线动作策略、任务队列、官方动作执行、回执、人工例外接管和撤销授权。

4. **阶段 D：经营学习闭环**

   完成对话跟进、渠道 ROI、成交回款归因和版本化效果评估。

### 成功指标

- 有效候选率；
- S/A 级线索准确率；
- 无证据断言率；
- 公开样本有效率、部分失败率和重复事件幂等率；
- 自动动作成功率和重复执行率（阶段 C）；
- 人工接管率与人工改判率；
- 回复、进入私域、报价、成交和回款转化率；
- 每条有效线索成本和每个成交客户获客成本；
- 渠道毛利 ROI 与回款周期；
- 客户撤销授权、拒绝和投诉率。

### 后续平台扩展

抖音能力完成后，快手、小红书、微博和微信公众号必须复用相同的 Connector、Event Evidence、Signal Aggregate、Action Policy、Receipt 和 Outcome 契约，只新增平台适配器与平台专属 Skill，不复制领域内核。
