## 关键设计决策

### 1. 不在当前工作区直接执行 `git pull`

当前未跟踪内容中包含需要保留的产品文档，也包含不应入库的依赖和构建产物。直接拉取虽然目前不一定产生文件冲突，但会把“升级基线”和“整理本地交付物”混成一次难以审查的操作。

### 2. 先建立文档封存提交

从当前 `9f7d154` 创建 `docs/ai-growth-specs`，只提交：

- 产品功能清单 Word 文档；
- 文档生成脚本；
- 新增的 `.gitignore`；
- 本设计和实施计划。

不得提交 `node_modules`、`dist`、`.DS_Store` 或 TypeScript 增量构建文件。

### 3. 从 Gitee 1.09 创建集成分支

从 `origin/master` 的 `5732e20` 创建：

```text
integration/gitee-1.09-ai-growth
```

随后只把文档封存提交 cherry-pick 到该分支。这样新分支的代码完全继承 Gitee 1.09，不把旧版代码重新合并一次。

### 4. GitHub 作为双人协作与评审入口

- Gitee `origin/master`：上游产品基线来源；
- GitHub `github/main`：双方协作、Pull Request 和 Codex 开发入口；
- 新集成分支先推送到 GitHub；
- 通过 Pull Request 审核后，再将 GitHub `main` 升级到 1.09 基线。

本阶段不回写 Gitee `master`，避免误改上游。

### 5. Pi 不进入确定性执行内核

Gitee 1.09 已经包含 Campaign、Strategy、Run、Worker、Provider Runtime、证据、去重、资格门禁和 CRM 转化。Pi 的后续位置调整为：

- 自然语言生成 ICP；
- 搜索策略规划；
- 信息不足判断；
- 客户研究；
- 客户作战卡；
- 结果解释；
- AI 增长参谋交互。

Pi 不负责租约、队列、重试、Provider 请求、CRM 写入或审核门禁。
