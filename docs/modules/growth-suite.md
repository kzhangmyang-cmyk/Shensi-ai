# Growth 经营模块

本页是桌面源码运行时中六个 Growth 经营入口的当前执行说明。历史方案只用于还原产品意图；真实行为以本页、OpenAPI 合同和当前源码为准。

## 1. 产品边界

核销明细的公开合同包含服务端生成的`id`及所属`allocationSetId`，退款以该`id`引用原付款明细，创建请求不接收客户端指定的明细ID。合同版本为1.0.36。MySQL模式提供现金核销创建/读取/生效API；付款、坏账和退款凭证以及目标收入必须已核验，并匹配商机、报价、币种和商业绑定。退款引用生效付款的精确集合及明细，事务内校验累计退款不得超过原付款；付款和坏账共同受目标收入金额上限约束，退款不作为新付款累计。

MySQL模式提供归因分配创建、按ID读取及生效接口。创建和读取需要`ledger.pending.create`，生效还需要`ledger.verify`及`If-Match: "attribution-set:<id>:<revision>"`。金额由服务端读取有效预算、已核验账目或来源报告后计算，不接受客户端金额；批次及证据按工作区校验。生效事务同时保存金额、操作人、幂等命令映射与生命周期事件，旧revision拒绝写入，重复命令不增加生效事件。

财务来源报告的创建和按ID读取已接入现有MySQL存储，服务重建后仍可读取及幂等重放。接口要求匹配的工作区与`ledger.pending.create`能力；来源报告列表尚未接通，报告持久化不替代关账的归因及证据核验。

财务、ROI 和委员会顶部提供独立企业资料阅读与报告入口。ROI 资料分析只引用已有证据；缺少投入、产出、期间或归因时显示定性建议和缺项，不代替下方基于真实批次数据的数值 ROI。文件选择先本地服务解析，显式模型分析后才可导出来源报告。

数值ROI仍待完整业务验收。MySQL运行模式保存批次及结算证据，绩效查询读取已发布的冻结快照，按工作区、币种、截止时间与封存序号选择；指定版本缺失不回退，无`pricing.sensitive.read`能力时隐藏金额。预计ROI读取正式审批报价（包含成员别名候选）及直接绑定批次、币种、有效期内的生效预算。计划筛选不自动分摊共享预算，缺少成本不生成收益率。

MySQL模式提供批次创建/列表/详情、绩效查询、证明签署及关账API。关账要求六类证明对应来源报告、已核验账目、生效归因和现金核销，并保留工作区、`roi.close`及幂等检查；If-Match格式见API索引。退款必须关联原付款且不得超过原付款金额。跨批次部分财务分配暂不支持，明确拒绝而非全额计入；重开API尚未接通。隔离MySQL正向关账、重复请求及模块重建读回已验证；发现与报价权威使用合成fixture，安装App完整业务及重启验收仍独立进行。资料分析与数值ROI是独立链路，不能互相替代验收。

结算MySQL仓库使用UTC格式读写结算版本及证明时间，快照、成员和凭证读取均按版本所属工作区过滤。`roi_closure_commands` 保存命令与结算版本的映射。关账服务将series一并交给仓库，使映射、版本、证据、状态推进和关账事件在同一事务提交；重复命令和旧revision均不能留下部分结果。底层单独保存版本不代表发布，绩效读取要求存在关账事件。该表由已有schema初始化入口创建，不清理或改写旧数据；缺少原始命令信息的历史版本不推造映射。关账/重开状态使用原revision进行条件更新，未更新时返回冲突；重开记录真实操作人并保留冻结快照。

六个入口组成一条连续的经营链，而不是六个孤立看板：

```text
增长顾问
  -> 客户目录（CRM 客户、来源、跟进和商机）
  -> 报价工作台（案例、版本、审批和发布状态）
  -> 财务经营（成本、财务事实和导入）
  -> ROI 经营分析（获客批次、币种、预计与已关账实际）
  -> 财务委员会（三表 package、六角色审计和人工审批）
```

产品、套餐和定价策略是报价的基础资料，不等同于客户目录。它们继续复用现有 Catalog API，但在客户目录中作为“产品与定价”辅助区域展示，不另造第二套 CRM。

具备 Catalog 管理权限时，空目录也能新增真实产品或服务，再为该项目创建基础定价草稿。表单包含币种、售价、成本、底价、利润率、折扣和账期，金额精确转为 minor；附加成本和赠品不在此入口编辑。套餐版本和定价策略仅允许草稿激活，保存不会自动激活；已启用的套餐版本可明确停用，已停用版本不可重新激活。写入使用资源级 ETag 和幂等键；网络结果不明时保留表单，同一内容重试沿用原请求和键，不重复创建草稿。离开页面取消请求并隔离迟到反馈。

报价列表按案例的 `open`、`closed`、`cancelled` 显示“进行中、已关闭、已取消”并筛选计数；案例状态不替代报价版本的草稿、审批和发布状态。

## 2. 原始意图与当前实现

原始设计见 `docs/archive/superpowers/specs/2026-07-26-ai-growth-advisor-demo-design.md`。它确定了“发现商机 -> 查看证据和作战卡 -> 人工审核 -> CRM 转换 -> 跟进任务 -> 经营结果”的主线，并明确不重做整个 CRM、不伪造真实状态。当前实现已经拥有 Growth bootstrap、工作区隔离、目录、报价、财务、ROI、增长顾问和财务委员会后端合同。

| 入口 | 当前权威来源 | 调查发现的核心缺口 | 当前决定 |
|---|---|---|---|
| 增长顾问 | `GET /api/v1/growth/advisor/today` 与建议决策接口 | 已绑定接受/忽略/完成与数据缺口导航；AI 解释继续复用经营总管，不伪造新对话协议 | 保留人工决策和真实服务端状态；空工作区展示真实的待准备状态与可执行导航，不补造建议、指标或历史记录 |
| 客户目录 | `/api/customers?scope=mine`、`/api/todos` 与现有私域/CRM controller | 已复用真实 CRM 客户列表和详情 | 产品目录作为报价辅助资料留在同页折叠区 |
| 报价工作台 | `/api/v1/quotes/*` | 获客商机继续复用已审核交接与资格评估；普通 CRM 商机由负责人填写需求、预算、决策人、成交概率和依据，生成独立的 `crm-quote-authority.v1` 快照 | 两条权威路径都进入同一套预览、草稿、正式提交和审批流程；客户级无商机案例仍只保存草稿。状态页签只负责筛选，真实案例计数只在列表摘要显示一次。 |
| 财务经营 | `/api/v1/acquisition/cost-*`、`/api/v1/finance/*` | CSV/XLSX 默认识别原表、多区域与原格；明确让 AI 读取后可向六角色追问，部分资料不要求先凑齐三表 | 明细入账是独立用途：列映射、预览、按字段汇总错误并明确确认；正式三表仍从智能体中心准备。浏览器不持久化原文件 |
| ROI 经营分析 | `/api/v1/acquisition/cohorts` 与 `/growth-performance` | 已保留获客批次列表并提供批次/币种/截止时间筛选 | 筛选栏固定显示紧凑中文“数据截至”日期；展开后使用可访问的原生时间控件按本机时区编辑至毫秒，查询保留该精度并转成 ISO；预计、实际和现金三口径采用关联的 ARIA 标签页，方向键、Home 和 End 会同步移动焦点与结果面板；只展示真实查询结果，无批次时导向获客中心 |
| 财务委员会 | package、run、专家、组合、审批和派发 API | 工作台完整；无 run 时展示三表前置条件与真实导航 | 创建仍只能由已验证 package 发起，不在空页绕过门禁 |

## 3. 参考实现与复用决定

调研只吸收产品和状态模型，不复制许可证不兼容的源码，也不引入新框架。

- [Twenty](https://github.com/twentyhq/twenty)：活跃的现代 CRM；借鉴统一客户、机会、活动和可配置视图。仓库采用 AGPLv3 加应用例外，当前不复制其代码。
- [ERPNext](https://github.com/frappe/erpnext)：成熟 ERP/CRM；借鉴 Lead/Customer/Quotation 分层、报价有效期与状态流。GPL-3.0，当前只借鉴流程。
- [ERPNext Quotation](https://docs.frappe.io/erpnext/quotation)：报价应绑定客户或线索、明细、价格、税费、有效期、交付和条款，并覆盖 draft/open/ordered/lost/expired/cancelled 生命周期。
- [PostHog Funnels](https://posthog.com/docs/product-analytics/funnels)：借鉴 cohort、时间窗、筛选和转化路径的可解释分析方式；不替换 Shensi 已有的财务闭包与归因模型。
- [Langfuse](https://github.com/langfuse/langfuse)：借鉴 agent trace/span/status/error/latency 的可观测性。核心为 MIT，但 `ee` 目录另有许可；当前继续使用已有 Pi 任务和 MySQL 状态，不新增运行时依赖。

## 4. 交互与视觉规则

- 沿用现有黑色壳、绿色强调色和 `--replica-*` token；Growth 页面不得再使用白色卡片、浅色正文或独立设计系统。
- 每个入口必须同时覆盖 loading、ready、empty、forbidden、conflict 和 error；空态必须解释数据从哪里来，并提供一个真实可执行的下一步。
- 读写动作必须显示真实服务端状态。没有请求、未提交、未完成时不得显示成功。
- 财务文件选择只保留本次页面内的原生 File 引用，表单重绘不丢失已选文件；更换文件或用途撤销旧预览。阅读用途展示区域、原格和缺项，不写账本；明细用途按真实字段/原因汇总错误，零有效行不可确认。离开页面清空 File、取消预览/读取/轮询，迟到结果不写新页面；已明确选择的只读资料 ID 只在同账号/工作区内存中供后续问答使用。完整规则见 `finance-document-reading.md`。
- 客户、报价、财务事实、ROI 和委员会运行都保留工作区隔离；不得用浏览器本地模拟数据补空。
- ROI 查询由每次挂载独立持有；新筛选取消旧查询，相同在途查询不重复发起，失败保留筛选和重试入口。旧响应不能覆盖新筛选或其他页面，现金指标读取契约的 `valueBps`。报告导出反馈绑定具体 runId/reportId，跨报告和离开页面后不显示旧任务结果。
- Growth 子入口激活时不再保留无关顶层模块的选中态；切换入口会回到内容顶部。
- 客户空态直接导向获客中心；经营总管识别到明确的抖音执行指令时，立即创建按负责人和团队隔离的服务端 AgentJob，并通过现有服务生成可核对的计划、来源、操作与预算快照。人工批准后后台 Run 独立继续。候选人回到同一经营总管面板后，用户可勾选多位待审核候选人并一次批准；服务端在同一工作流串行执行每位候选人的已授权 CRM 交接，逐人保留决策版本、幂等键、Customer 和 Todo 审计结果，部分失败后重试不会重复写入已完成的候选人。评论与私信批次是独立的对外触达流程，不是 CRM 批量交接的前置条件。页面重开从服务端恢复，不依赖 localStorage 或跨页面点击。
- 对外评论、私信、付款、报税、记账和删除仍遵守现有人工确认与权限边界。

## 5. 实施顺序与验收

1. 客户目录复用真实 CRM，并保留产品与定价辅助区域。
2. 报价工作台接通普通 CRM 人工评估与获客证据评估两条入口，以及案例创建、产品/定价选择、预览、草稿、提交和审批；每次写入使用真实 ETag 和幂等键。
3. 财务经营接通导入预览/提交。
4. ROI 接通筛选与真实查询。
5. 增长顾问接通建议决策和经营总管解释。
6. 财务委员会补可执行入口和最近运行，不绕过三表 package 门禁。

每一阶段至少通过：

```bash
pnpm --filter goodjob-crm-frontend run contract:check
pnpm --filter goodjob-crm-frontend run test:types
pnpm --filter goodjob-crm-frontend test
pnpm --filter goodjob-crm-frontend build
git diff --check
```

文件选择、拖拽、表单重绘、错误反馈及明确确认的隔离浏览器回归：

```bash
pnpm --dir frontend exec playwright test --config=playwright.finance-import.config.ts
```

该测试使用纯合成文件与隔离接口响应，不上传真实财务材料；它不替代原生文件选择器或真实 MySQL 验收。

涉及真实 MySQL 的财务委员会纵向验收还需按 `frontend/README.md` 提供独立测试管理连接；未提供时必须如实标记为未执行，不能以 fixture 代替。

当前源码验收（2026-09-07）已经使用隔离的本地 MySQL 管理连接完成：增长顾问 MySQL 7/7、财务 MySQL 22/22、ROI MySQL 9/9；受控财务委员会 real-runtime 5/5 覆盖运行创建、分析、人工审批、派发回执和跨运行时恢复。另有隔离 HTTP 验收覆盖三表预览、正式提交、现金预测和委员会 `snapshot_frozen` 创建。后者没有可用的测试模型连接，因此只证明真实 API/MySQL 创建链，完整处理证据仍以前述受控 real-runtime 测试为准。

## 6. 暂不实施的扩展

- 自定义客户字段与任意视图构建器；
- 复杂 CPQ 规则编辑器；
- 财务数据仓库或新 BI 引擎；
- 新 agent 编排框架（本轮复用现有 Copilot 任务、计划、运行和 CRM 交接服务）；
- 自动执行外部社交或财务动作。

这些能力只有在当前闭环稳定且有真实业务样本后再评估。
