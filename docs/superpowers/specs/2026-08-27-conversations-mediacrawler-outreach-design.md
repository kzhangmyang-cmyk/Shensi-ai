# 社媒对话 MediaCrawler 受控外联设计

状态：对话中已确认使用 MediaCrawler；等待书面设计复核

日期：2026-08-27

仓库：`shensi`

范围：抖音真实会话页面、外联批次恢复、MediaCrawler 评论与私信执行

## 1. 目的

把真实会话页面从只读公开证据视图补成可恢复的受控外联工作台。用户可以从
MediaCrawler 已采集的真实候选证据中选择一位候选，生成评论与私信草稿，逐条编辑，
保存不可变修订，并在页面明确二次确认后让服务器依次执行评论和私信。

本功能复用既有获客批次、审批、动作 outbox、每日限额和 MediaCrawler 登录态，不新建
第二套发送权威。页面刷新或重新进入后，能够从服务器恢复候选对应的最近批次、草稿、
审批状态和动作回执。

这里的“社媒对话”表示基于公开候选证据发起受控外联，不冒充抖音官方 inbox，也不把
尚未接入的私信收件箱或评论线程伪装成真实会话。

## 2. 已选方案

使用 `services/media-crawler/` 中已授权的 MediaCrawler fork 及 Shensi 扩展层：

- MediaCrawler 负责抖音登录态、浏览器进程、页面导航和单动作执行；
- Node 后端负责候选、证据、批次修订、审批、额度、动作顺序、幂等和审计；
- 前端只提交候选 ID、人工编辑后的精确文案及显式审批，不接触 Cookie、账号句柄或
  浏览器路径；
- 评论先执行，只有评论成功且最短等待时间已满足，私信才可被 worker 领取；
- CAPTCHA、滑块、重新登录、风控提示、页面歧义或控件缺失都安全暂停；可见浏览器允许
  用户本人完成平台验证，系统复检通过后恢复原动作，但不自动识别、破解或绕过验证。

不采用只解除按钮的 UI 方案，因为它无法在刷新后恢复批次，也无法证明真实页面动作
可以执行。不在本次切换到抖音官方 OpenAPI；官方适配器可以以后实现相同内部动作端口，
但不改变本设计的批次和审批合同。

## 3. 第三方与授权边界

本功能沿用 `2026-08-24-douyin-mediacrawler-acquisition-design.md` 的来源和授权约束。
MediaCrawler 的上游定位是采集器；评论和私信执行属于 Shensi 扩展，不能描述为上游
自带能力。运营方已表示获得商业授权；仓库只记录授权引用，不提交包含私人信息的授权
文件。

不得复制新的规避检测、代理轮换、验证码处理或私有签名实现。真实写动作仅使用当前
显式授权账号的持久浏览器会话和页面可见控件。

MediaCrawler 作者对源码的授权不替代抖音对账号和验证流程的要求。平台验证只能由账号
操作者在可见浏览器中手动完成；系统不得代替用户解题、注入验证令牌或调用规避服务。

## 4. 用户流程

```text
打开社媒对话
→ 读取抖音任务的可用候选证据与对应最近批次
→ 选择一位具有精确 /video/{id} 证据的候选
→ 生成单候选待审批批次（不会发送）
→ 编辑精确公开评论与精确私信
→ 保存新修订并重新检查
→ 勾选“我已逐条核对”
→ 确认审批并排队
→ MediaCrawler 执行公开评论
→ 服务端保存评论回执并等待最短间隔
→ MediaCrawler 执行私信
→ 页面轮询并展示成功、失败或风险暂停回执
```

一条公开证据只能创建包含其自身的单候选批次，避免跨运行选择和隐式批量发送。批量
能力继续留在获客中心。

只有精确 `https://www.douyin.com/video/{id}` 证据可创建批次。主页证据仍可阅读，但
操作按钮必须显示“缺少可评论视频”，并保持禁用。前端资格判断只用于提示；后端创建与
审批仍重新验证候选、DNC、视频、主页、登录版本、额度、证据哈希和策略版本。

## 5. 前端设计

真实会话控制器组合既有 `OutreachBatchController`，不复制审批领域逻辑。页面保持当前
黑色、灰色和绿色视觉变量，复用现有外联编辑器与时间线样式。

页面状态包括：

- 公开互动读取状态与当前候选；
- 当前候选是否具有可评论视频；
- 当前候选关联的最近批次摘要；
- 完整批次状态、草稿、冲突、动作回执和错误；
- 创建、保存、审批和刷新期间的忙碌状态。

页面行为包括：

- 选择候选不会发送任何动作；
- “生成待审批批次”只调用创建接口；
- 评论与私信编辑复用现有完整批次修订接口；
- 审批按钮必须同时满足批次仍为 `awaiting_approval`、用户勾选复核框、当前没有进行中的
  请求；
- 导航离开页面时停止读取和回执轮询，重新进入后从服务器恢复；
- 409/412 修订冲突重新加载权威批次，并要求再次复核；
- 用户可查看精确来源链接、动作顺序、尝试次数、平台回执或安全失败码。

文案统一为“公开证据外联”“评论与私信”，不使用“回复这条私信”等无法由现有数据
证明的说法。

## 6. 后端批次发现接口

新增只读分页接口：

```text
GET /api/v1/acquisition/outreach-batches
  ?runId={runId}
  &candidateId={candidateId}
  &limit={1..50}
  &cursor={opaque}
```

调用方必须至少提供 `runId` 和 `candidateId`，服务端验证二者属于当前 workspace。返回
匹配批次当前 head revision 的有界摘要，按 `createdAt DESC, id DESC` 稳定排序；游标由
服务端签名或编码，浏览器不能提交任意排序字段。响应不包含浏览器凭证、账号句柄、完整
审计内容或私有页面数据。

该 GET 要求登录、workspace 和 `acquisition.outreach.approve` 能力，不要求 CSRF 或
幂等键。MySQL 仓储增加 workspace/run/candidate/head 的查询索引；内存仓储提供相同
分页语义。现有按 batch ID 读取、修订、审批和动作查询接口保持不变。

前端打开候选时先查询最近批次；若没有批次才显示创建入口。`sessionStorage` 只作为
体验优化，服务器查询才是恢复权威。

## 7. MediaCrawler 动作执行

动作 worker 继续向私有 sidecar 提交一个封闭的单动作命令：动作 ID、账号不透明句柄、
动作种类、精确目标 URL、精确冻结文案和幂等摘要。sidecar 不接受浏览器提供的 Cookie、
选择器或任意脚本。

### 7.1 公开评论

1. 在账号专属持久浏览器上下文打开精确视频 URL。
2. 校验最终主机、视频 ID 和登录状态未变化。
3. 检测 CAPTCHA、滑块、风控横幅、登录过期和访问限制。
   检测到验证时将动作标记为 `risk_paused`，保留动作 ID、目标和冻结文案，在 Shensi
   页面显示“需要在抖音窗口手动完成验证”。用户完成后只能通过受控恢复操作触发重新
   探测；恢复不会创建新动作，也不会跳过后续目标和文案校验。
4. 通过有序定位策略查找页面可见评论编辑器：语义角色/可访问名称、稳定页面属性、
   最小受控 DOM 结构；测试专用 `data-e2e` 只能作为 fixture 分支，不能作为真实页面
   唯一定位方式。
5. 要求目标控件唯一、可见、可编辑，填入精确冻结文案并回读确认字节等价。
6. 定位唯一可用提交控件，提交一次。
7. 等待页面确认或当前账号新评论的可验证出现，保存有界平台回执引用；无法确认时返回
   不确定失败，不重复盲发。

### 7.2 私信

1. 仅领取已具有成功评论回执且等待间隔已满足的动作。
2. 打开冻结的精确用户主页并校验主机与主体标识。
3. 检测登录、权限、风控和不可私信状态。
4. 通过相同的唯一可见控件原则进入私信页面、定位编辑器、填入并回读精确冻结文案。
5. 提交一次，等待可验证的本地发送状态或消息出现并保存回执。

真实定位策略集中在单独 adapter 中，页面探测与实际点击分离，便于对 DOM 变化做无写
探测。任何多匹配、无匹配、文本不一致、导航异常或回执不确定都返回稳定错误码并
fail closed。错误、日志和 API 响应不记录完整私信、Cookie、页面 HTML 或浏览器状态。

## 8. 错误与恢复

稳定错误至少区分：

- 登录失效或账号版本变化；
- 候选已 DNC、证据过期或目标 URL 不再精确；
- 页面控件缺失或存在歧义；
- CAPTCHA/滑块/平台风控；
- 评论不可用、私信不可用；
- 已提交但回执不确定；
- 网络超时、sidecar 不可用；
- ETag 冲突、审批状态变化、额度不足。

回执不确定不得自动重试外部写动作。操作员先在可见浏览器确认平台状态，再使用受控恢复
流程。已成功的评论不会因私信失败而重发。worker 重启后继续使用已有 lease、动作幂等
标识和平台回执事实，不创建新批次。

平台验证与普通暂时错误不同：系统只允许“等待用户手动完成 → 无写复检 → 恢复原动作”，
不提供自动过滑块、验证码识别、令牌注入或第三方打码服务。恢复前若已经出现同一动作的
精确评论回执，原动作直接收敛为成功，不再点击提交。

## 9. 测试策略

所有生产修改遵循 red-green-refactor：先写会因缺少行为而失败的测试，再实现最小通过
代码。

自动测试不得访问或写入真实抖音账号。覆盖包括：

- 社媒对话的可评论/仅查看候选、单候选创建、编辑、复核门禁、审批和回执展示；
- 页面刷新后的批次发现与恢复、分页、租户隔离、权限和游标校验；
- 修订冲突、DNC、证据变化、额度、登录版本和动作开关 fail closed；
- MediaCrawler fixture 中真实定位优先级、唯一控件要求、精确文案回读、一次提交、
  评论回执、私信前置和风险暂停；
- 缺失控件、多控件、导航到错误 ID、验证码、提交后回执不确定时不重复发送；
- 验证出现时不调用识别或绕过逻辑，用户手动完成后的无写复检能够恢复同一动作；
- 路由切换后不发生陈旧渲染或继续轮询；
- XSS、私密字段和日志泄漏回归。

发布验收只验证登录、读取、创建批次、编辑、保存和二次确认门禁，不在自动验收中点击
最终审批。真实评论/私信只由用户在页面检查精确文案后亲自进行第二次确认。

## 11. 完成标准

- 真实会话页面不再显示“发送不可用”占位框；
- 可评论候选能创建单候选批次，profile-only 候选仍安全禁用；
- 草稿可编辑、可保存为新修订，审批必须再次勾选复核；
- 刷新后能从服务器恢复当前候选的最近批次和动作回执；
- 最终审批仍是唯一外部发送授权；
- fixture 证明 MediaCrawler adapter 不依赖测试专用选择器且错误时不点击；
- fixture 必须证明公开评论能在真实页面结构模拟中精确填入、只提交一次并取得可验证
  回执；缺少这条通过证据不得宣称评论功能完成；
- 构建、合同、前后端单测、sidecar 测试和无外部写 E2E 全部通过；
- 当前文档不再描述社媒对话为永久只读；
- 发布验收不产生真实评论或私信。

自动验证通过后，真实评论还需要一次由用户选择目标、核对精确文案并亲自二次确认的
受控验收。只有平台页面出现该评论且服务器保存可验证回执，才把真实评论链路标记为
已验收；Codex 不代替用户执行最终审批。
